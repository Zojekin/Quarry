# 题匣 (Quarry) 自动化开发流水线规范 (Automation Pipeline Specification)

本文档定义了题匣项目基于 T3 Code 与多智能体协同的无人值守研发、缺陷修复、质量优化与代码审查标准。

---

## 1. 核心架构与模型分工 (Five-Role Architecture)

本项目采用 **“思考规划与执行编码解耦（Planner-Executor Separation）”** 与 **“双重质量门禁（Dual Quality Gate）”** 机制：

```
┌─────────────────────────────────────────────────────────────┐
│       总指挥 / 架构师 (Planner - 高阶推理规划模型)          │
│   - 定时巡检 GitHub Issues，根据标签分流                    │
│   - 研读 memory-bank 架构文档，编写《任务实现规格书》       │
└──────────────────────────────┬──────────────────────────────┘
                               │ delegate_task (isolation: 'worktree')
                               ▼
┌─────────────────────────────────────────────────────────────┐
│          三大专职执行工人 (Workers - Codex / GPT)           │
│   - 功能开发工 (Feature Worker)  [label: feat]               │
│   - 缺陷修复工 (Bug Worker)      [label: bug]                │
│   - 质量重构工 (Quality Worker)  [label: optimize]           │
└──────────────────────────────┬──────────────────────────────┘
                               │ pnpm test & build 全绿通过
                               ▼
┌─────────────────────────────────────────────────────────────┐
│          门禁质检员 (Reviewer / Gatekeeper)                 │
│   - 调取 git diff 审查架构合规性、代码纯洁度与测试有效性    │
│   - 发现问题内部打回修改；完全达标后生成正式 PR 提交 GitHub │
└──────────────────────────────┬──────────────────────────────┘
                               │ Pull Request
                               ▼
┌─────────────────────────────────────────────────────────────┐
│             用户 (User) 手机/网页端一键 "收菜" 🌾           │
└─────────────────────────────────────────────────────────────┘
```

## 2. 标签路由与智能体职责 (Issue Routing & Roles)

用户在 GitHub 提 Issue 时只需附带对应标签，调度器将自动分配对应工人：

### 2.1 功能开发工 (Feature Worker) —— `label: feat`
* **适用场景**：新功能、新组件、新业务逻辑开发。
* **执行要求**：
  1. 严格按照架构师的技术规格实现，禁止私自篡改未声明的文件；
  2. 必须补写对应功能的新单元测试，保证新增分支被充分覆盖；
  3. 分支命名：`feat/issue-<id>-<简短描述>`。

### 2.2 缺陷修复工 (Bug Worker) —— `label: bug`
* **适用场景**：Bug 修复、计算错误、界面异常、CI 崩溃排查。
* **执行铁律 (TDD 防御机制)**：
  1. **第一步（Red）**：必须先在对应测试目录编写一个能够**稳定复现该 Bug** 的单元测试（此时执行测试必须失败）；
  2. **第二步（Green）**：修改源码修复该 Bug，直至该复现测试成功转绿；
  3. **第三步（Regression）**：运行全仓测试，确保原有 147+ 项测试 100% 保持通过；
  4. 分支命名：`fix/issue-<id>-<简短描述>`。

### 2.3 质量重构工 (Quality Worker) —— `label: optimize`
* **适用场景**：代码异味消除、解耦重构、性能调优、补齐测试用例。
* **质量工三大红线**：
  1. **严禁破坏公共契约**：禁止修改 `packages/shared` 的 API 签名和公共数据结构；
  2. **严禁功能降级**：所有原有测试必须全部通过，不允许通过修改断言来“掩盖”测试失败；
  3. **必须遵循 AGENTS.md**：降低模块交叉引用，统一命名规范；
  4. 分支命名：`refactor/issue-<id>-<简短描述>`。

## 3. 门禁质检员审查清单 (Reviewer Checklist)

在任何 PR 正式推送到 GitHub 之前，质检员必须逐一确认以下五项指标：

1. **架构合规**：未破坏系统的四道核心解耦防线（Web 纯净性、后端客户端独立性、SQLite 仓储隔离、附件存储虚拟化）。
2. **代码纯洁**：全量代码无残留的 `console.log`、无调试临时文件、无无用注释代码。
3. **测试真伪**：新加的测试用例具有实际断言意义，非空断言（dummy test）。
4. **编译构建**：在独立工作区内执行 `pnpm lint`、`pnpm test`、`pnpm build` 无任何 warning 和 error。
5. **文档同步**：若涉及重大功能落地，同步确认 `memory-bank/architecture.md` 与 `memory-bank/progress.md` 已准确更新。

若质检不合格，质检员立即在流水线内部打回给对应 Worker 重新修改；完全合格后方可调用 `pull_request_create`。

---

## 4. 防冲突与熔断保护 (Safety Mechanisms)

* **物理隔离**：所有 Worker 必须通过 T3 Code `delegate_task` 的 `isolation: "worktree"` 模式启动，各自分配独立物理工作区，杜绝文件锁死和代码踩踏。
* **PR 熔断**：仓库中未合并（Open）的 PR 数量上限为 **2 个**。达到上限时，流水线停止派发新需求，自动进入等待状态，防止 PR 泛滥造成评审堆积。
